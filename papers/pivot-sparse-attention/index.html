看懂 PIVOT：一排 query 拼一次单，稀疏注意力的「索引员」不再重复跑腿

腾讯团队发现：DeepSeek Sparse Attention（DSA）把主注意力算快了，瓶颈却转移到了「给每个 query 挑 top-k token」的索引器上——而相邻 query 挑出的 top-k 其实高度重叠。PIVOT 让一排相邻 query 拼成一个「代理 query」，只扫一遍前缀，免训练、即插即用，索引器最高提速约 4.8 倍，精度与稠密索引器持平。

第 0 章

热身：稀疏注意力把账算省了，却把账单转给了「索引员」

上下文冲向百万 token 的时代，全注意力的 O(L²) 算不起了；DSA 让每个 query 只看 top-k 个 token——但「挑哪 k 个」这件事本身，还得把整段前缀翻一遍。

📚 先回顾：DSA 的「索引器 + 稀疏注意力」两段式

全注意力里，每个 query（当前正在处理的 token）都要和前面所有 token 算注意力，序列长 L 时代价是 O(L²)。DeepSeek Sparse Attention（DSA）的做法是加一个很轻的索引器（lightning indexer）：对位置 t 的 query，给它前面每个 token s 打一个相关性分数（论文 Preliminary §Background，式 (1)）：

It,s = ∑j=1HI wIt,j · ReLU( qIt,j · kIs )
白话翻译：索引器有 HI 个轻量「头」，每个头算一次点积、过一道 ReLU（负数清零），再按权重 w 相加。分数最高的 k 个 token 入选集合 Tt，下游的 Sparse MLA 只对这 k 个 token 算注意力。

这样一来，主注意力的代价从 O(L²) 降到 O(Lk)（k ≪ L，论文实验中 k = 2048）。这套设计支撑了 DeepSeek-V3.2、GLM-5.1 这样的生产级模型（论文 §Introduction）。

DSA 像一家大型图书馆请了一位「索引员」：读者（query）不用亲自翻遍所有书架（全注意力），索引员先挑出 k 本最相关的书，读者只精读这 k 本。读者的阅读时间大大缩短——但索引员自己，仍然为每位读者把整座图书馆从头到尾走了一遍。

💸 瓶颈转移：索引器从「小前菜」变成「主菜」

问题恰恰出在索引员身上：它给每个 query都要对整个前缀打分。整段序列加起来，每层的索引代价仍是 O(L²)（prefill 阶段），decode 阶段每步 O(L)（论文 Preliminary §Cost）。上下文越长，这份账单越刺眼：

阶段索引器占端到端延迟比例（200K token 时）
Prefill（预填充）约 81%
Decode（逐字生成）约 41%

已有的加速工作各砍一刀：HISA 砍 token 轴（先筛块再筛 token）、MISA 砍 头轴（只激活部分索引头）、IndexCache 砍 层轴（相邻层复用 top-k）。但它们都没碰 query 轴——索引器仍然为每个 query 单独跑一遍全前缀扫描（论文 §Introduction、§Related Work）。

PIVOT 的核心主张：索引器在 query 轴上存在大量重复劳动。相邻 query 挑出的 top-k 高度重叠，完全可以一排 query 共享一次前缀扫描——这是与前三个轴正交的「第四条加速轴」（论文 §Introduction 贡献 1）。
第 1 章

三个观察：为什么「拼单」是安全的

作者在 DeepSeek-V3.2、RULER-QA 128K 上解剖了索引器的行为（k=2048），发现三条性质：O1 让共享成为可能，O2 让共享足够便宜，O3 让共享不掉精度。

🔎 O1：相邻 query 的 top-k 高度重叠

把任意两个 query 的 top-k 集合求交集、画出热力图，会看到一条明亮的对角线带：相邻 query 选中的 token 几乎一样。相邻位置的重叠率达 0.8–0.9；即便把 4 个连续 query 合成一组，它们共同选中的比例（中位数）从浅层到深层也有 65%–78%（L3/L30/L58 三层均如此）（论文 §Observations O1，图 2a）。

原因很直觉：相邻 query 共享几乎相同的前缀、隐藏状态也相近，所以它们眼中「重要的 token」只会缓慢漂移，不会突变。附录 C 进一步验证：这条亮带在浅、中、深层都存在，且随 query 距离优雅衰减——局部性强，但不会延伸到任意远，所以「小组共享」合理、「全局共享」不行（论文附录 C，图 5）。

同一节车厢里坐前后排的四个读者，读同一本书时划的重点段落八九不离十——让他们各自把整本书重翻一遍找重点，纯属浪费。

🧺 O2：一整组 query 的 top-k 并集，远比想象的小

一组 g 个 query 的 top-k 并集，理论上最小 k（大家选得完全一样）、最大 g·k（完全不重叠）。实测它紧贴下限：g=4 时并集只有 1.3–1.5 × k，而且随 g 亚线性增长，g=16 也才 1.7–2.4 × k，远低于最坏情况的 16 × k（论文 §Observations O2，图 2b）。拖动滑杆看实测数字：

实心柱为三个层（L3 浅 / L30 中 / L58 深）实测的「组 top-k 并集 ÷ k」，虚线为最坏情况 g·k（完全不重叠）。数据摘自论文图 2b（DeepSeek-V3.2，RULER-QA 128K，k=2048）。PIVOT 默认候选预算 c = 2k，刚好盖住 g=4 时的并集。
这组数字直接决定了 PIVOT 的候选预算：既然 g=4 的并集只有约 1.5 × k，那么一个 c = 2k = 4096 的共享候选集就足以「装下」全组需要的 token（论文 §Method、§Experimental Settings）。

📉 O3：索引分数是长尾的——少数 key 拿走绝大部分分数

把索引分数沿 key 轴排序画出累计质量曲线：曲线先陡升、迅速变平——一小部分 key 就携带了绝大部分分数质量，远不到 k/2、3k/4 就已饱和。成因就在式 (1) 的 ReLU：点积接近零均值，ReLU 把负贡献清零，只有在许多头上都「正对齐」的 key 才能累积出高分（论文 §Observations O3，图 2c）。

像搜索引擎的结果分布：真正相关的网页集中在第一页，后面几亿条「匹配结果」的得分几乎为零。所以只要候选集覆盖「第一页」，在里面重新精排，结果和翻遍全网几乎一样。

这条性质是 PIVOT-Refine 不掉精度的关键：每个 query 真正高分的 token 几乎都在共享候选集 C 里，在 C 上重新打分选 top-k，就逼近了全前缀扫描的结果（论文 §Method PIVOT-Refine）。

三条性质的分工：O1 让一个「代理 query」能代表全组（能共享）；O2 让候选集预算可以很小（共享得起，k < c ≪ L）；O3 让候选集内重排足够准（共享不掉精度）（论文 §Observations 末段）。
第 2 章

核心方法：PIVOT 怎么「拼单」

全称 Proxy Indexing Via One full-prefix Traversal——「一次全前缀遍历的代理索引」。把一组合成一个代理 query，扫一遍前缀，然后每个 query 从共享结果里取自己的 top-k。

🎬 一眼看懂：g 次全扫描 → 1 次共享扫描

DSA 里，一组 g 个 query 各自独立扫描全部前缀，代价 O(gL)；PIVOT 把全组聚成一个代理 query（proxy query），只扫一次，然后两个变体二选一：PIVOT-Reuse 直接把代理的 top-k 发给全组（最快）；PIVOT-Refine 保留代理的 top-c 候选集，每个 query 用自己的索引器在候选集内重新打分、各选各的 top-k（更准）（论文 §Method，图 3）。点下面的按钮，直观对比三种流程的「打分次数」：

示意参数：前缀 L = 120 格、g = 4 个 query、k = 12、候选预算 c = 2k = 24——比例与论文默认（k = 2048、c = 4096、g = 4）一致。蓝格 = 全前缀扫描，橙格 = 候选集内重打分，绿格 = 最终 top-k。真实场景 L 可达 25.6 万格，差距随之急剧放大（见第 3 章实测）。
DSA 像四位邻居各自开车去同一个批发市场采购；PIVOT-Reuse 是派一位代表集中采购、四家分一样的货；PIVOT-Refine 是代表先拉回一车「候选商品」，每家再按自己的清单挑一遍——多花几分钟，但每家的货更合身。

👥 第一步：分组——两个阶段，两套「拼单」方式

PIVOT 只把「同一时刻可得」的 query 编成组，一步之内摊销一次代理扫描，不跨步留状态（论文 §Method Grouping）：

阶段怎么分组组大小 g
Prefill（预填充）所有位置同时可得，按位置连续切成固定大小的组：G = { qt, qt+1, …, qt+g−1 }默认 g = 4
Decode（逐字生成）直接搭 MTP（多 token 预测）的便车：当前 token + 同一步产出的 d 个草稿 token 天然成组g = d + 1 = 4（d = 3）

Decode 阶段本来一次只生成一个 token、没有天然的组，而 DeepSeek-V3.2 与 GLM-5.1 在生产中都开了 MTP——同一步里这些 query 反正都要算，PIVOT 零成本蹭上现成的组，与 MTP 的加速互相叠加而非竞争（论文 §Method Grouping，式 (2)(3)）。

Decode 阶段像每站只上一位乘客的公交，凑不成团；MTP 本来就在每一站「预售」了后面 3 张票，PIVOT 直接把这一站连人带预售票共 4 位拼成一车。

🤖 第二步：代理 query = 全组的「逐头平均」

把组内所有成员的索引 query 和门控权重按头做平均，得到一个代理 query（论文 §The Shared Proxy Scan，式 (4)(5)）：

q̄Ij = 1g ∑t′∈G qIt′,j，   w̄Ij = 1g ∑t′∈G wIt′,j
白话：每组请一位「平均脸」代表。它用式 (1) 的同一个索引器对整个前缀只扫一遍，打分截止在组内第一个位置，保证对全组成员都满足因果性。消融实验（表 2）表明均值聚合明显优于「派第一个/最后一个 query 当代表」。

这一次扫描的代价是 O(L)，由全组共享；之后不再碰完整前缀。

🔀 第三步：两个变体，一道「速度—精度」选择题

PIVOT-Reuse（更快）：跳过精修，直接把代理分数的 top-k 分配给组内每个 query（式 6）：

Tt = TopK({ Īs | s ≤ t }, k)，∀t ∈ G
全组共用同一份 top-k。零逐 query 打分，整组代价 O(L)。

PIVOT-Refine（更准，默认）：先取代理分数的 top-c 作共享候选集 C（c = 2k），每个 query 用自己的索引器在 C 内重新打分、各选 top-k（式 7–9）：

C = TopK({ Īs }, c)，  Tt = TopK({ It,s | s ∈ C }, k)
精确打分只发生在 c 个候选上，每组多花 O(gc)，总代价 O(L + gc)。
方案每组索引代价特点
DSA（稠密索引器）O(g·L)每个 query 都扫全前缀
PIVOT-ReuseO(L)最快；极端长上下文会损失少量召回
PIVOT-RefineO(L + g·c)默认；精度追平稠密，代价介于两者之间（c ≪ L）

工程上还有两个细节：每个 query 会额外并入一个局部窗口（最近的 W = 4 个 token），因为「离自己最近的 token」恰恰是代理最难代表的（论文附录 B）；另外设有短序列护栏——组起始位置小于 c 时直接回退稠密扫描，保证 PIVOT 在部署中永远不会比 DSA 慢（论文附录 E，Algorithm 1）。

接口零改动：索引器与下游 Sparse MLA 之间只通过索引集合 Tt 通信，PIVOT 只改变 Tt 的产生方式——Sparse MLA 算子、k 的大小、KV cache 全部原样不动；把 g 设为 1 就精确退化为原始索引器（论文 §Method、附录 A）。
第 3 章

实验结果：精度持平，速度随上下文越拉越开

两个生产级模型（DeepSeek-V3.2、GLM-5.1）× 两套长上下文基准（LongBench、RULER），PIVOT-Refine 全程贴着稠密 DSA 的精度，索引器 kernel 最高提速约 4.8×，端到端最高 1.61×。

🧪 实验怎么搭的

模型：DeepSeek-V3.2 与 GLM-5.1——两个都采用 DSA 索引器的生产级模型，均开 MTP（深度 d = 3，decode 组大小 g = 4）。基准：RULER（4K–128K 合成检索/推理）与 LongBench（真实长文档任务）。基线：稠密 DSA 索引器，以及两条正交加速轴的代表 HISA（token 轴）、IndexCache（层轴）。实现：vLLM + NVIDIA H20；k = 2048，c = 2k = 4096，prefill g = 4，代理用均值池化（论文 §Experimental Settings）。

🎯 精度：RULER 128K 拉开差距的地方，Refine 贴住稠密基线

端到端口径：短上下文时索引器占比小，PIVOT 与基线基本持平；长上下文时索引器成为大头，两个变体端到端最高达约 1.6×（论文 §Efficiency Results，图 4c）。kernel 拆解（附录 D）还显示：随上下文变长，Refine 的开销大头从「逐 query 重打分」转移到「代理扫描」本身——重打分被逐渐摊薄。

第 4 章

局限与意义

PIVOT 不是让索引「免费」，而是承认「相邻 query 想要的基本相同」之后，不再为每个 query 重复跑腿。

⚠️ 需要知道的边界

边界说明
短上下文不划算Refine 在 8K prefill 只有 0.55×（比重跑稠密还慢），加速收益集中在长上下文；论文用短序列护栏（回退稠密）兜住这个区间
组不能贪大g=16 时 Reuse 在 128K 掉到 65.16——共享选择盖不住越来越分散的组内需求（O2 的边界）

验证范围有限目前只在两个 DSA 系模型（DeepSeek-V3.2、GLM-5.1）上验证；decode 分组依赖 MTP，没开 MTP 的模型享受不到 decode 侧收益
证据分散的任务略弱多文档 QA 这类「四处取证」的任务上 PIVOT 略低于稠密基线，组级代理对这类 query 的代表性较差

🌟 为什么这项工作值得读

它的贡献不在于又发明了一个更复杂的索引器，而在于指出了一条被所有人忽略的加速轴：此前的工作把 token 轴、头轴、层轴都砍了一遍，唯独每个 query 仍然各扫一遍全前缀。PIVOT 用三张观测图（O1 重叠、O2 小并集、O3 长尾）证明 query 轴上存在系统性冗余，并给出一个免训练、不动下游算子、prefill/decode 通吃的极简方案（论文 §Introduction、§Conclusion）。

四条轴可以叠加：PIVOT 与 IndexCache 组合（+IC）已验证可行；作者把「query 轴 × token/头/层轴的组合」与「推广到更多模型家族」列为未来方向（论文 §Conclusion）。
